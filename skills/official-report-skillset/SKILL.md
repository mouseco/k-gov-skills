# official-report-skillset

공공기관 보고서는 창작 글이 아니라 **의사결정 문서**다. 목적은 읽는 사람이 상황을 이해하고, 판단하고, 다음 조치를 정할 수 있게 만드는 것이다.

```text
근거 확인
→ 쟁점이 크거나 출처 있는 심층 판단이 필요하면 deep-research-pro 방식 보조
→ 문서 유형 판별
→ 작성 기법 선택
→ 공문서 보고서 초안 작성
→ 논리·누락 검토
→ 한글 문장 교정
```

---

## 0단계. 심층 근거조사 연동 판단

공공기관 보고서 작성셋은 단독 초안 작성보다 **근거 확보와 판단 구조화**가 먼저 필요한 경우가 많다. 다만 범용 아이디어 정리·일반 자료수집 스킬은 사용하지 않고, 보고서셋 내부 기준과 `deep-research-pro` 방식만 사용한다.

| 상황 | 적용 방식 | 가져올 부분 | 제외하거나 축소할 부분 | 산출물 |
|---|---|---|---|---|
| 요청이 아이디어 수준이거나 목적·범위·독자·성공 기준이 불명확함 | 보고서셋 내부 판단 | 목적, 제약, 성공 기준, 대안 2~3개, 추천안과 trade-off 정리 | 과도한 질의 반복, 제품/개발 설계 방식 | 작성 방향, 쟁점, 대안 구조 |
| 쟁점이 크고 출처 있는 심층 보고서가 필요함 | `deep-research-pro` 방식 | 연구 질문 3~5개 분해, 다중 출처 교차확인, 주요 출처 본문 확인, 인용 포함 요약, 신뢰도·한계 표시 | `/home/clawdbot/.../ddg` 등 리눅스 경로·전용 DDG 스크립트, `~/clawd/research` 저장 경로 | 심층 근거 메모, 출처 포함 요약, 판단 한계 |
| 사용자가 자료 없이 “그럴듯한 보고서”만 요청함 | 보고서셋 내부 판단 → 필요 시 `deep-research-pro` 방식 | 먼저 보고서 질문을 좁히고, 그다음 필요한 근거만 선별 | 자료를 15~30개씩 기계적으로 모으는 방식 | 보고서 설계안 + 근거 메모 |

공공기관 보고서용 근거 우선순위:

1. 법령·시행령·고시·지침·내부 규정
2. 정부·공공기관 공식 발표자료와 보도자료
3. 통계청·부처·공공데이터 등 공식 통계
4. 국회·감사·평가·연구기관 보고서
5. 유사 기관 사례
6. 언론·업계 동향
7. 커뮤니티 반응은 민원·수요·현장 의견 확인이 필요할 때만 제한적으로 사용

심층조사가 필요한 경우:

- 단순 근거 확인은 보고서셋 내부 기준으로 처리한다.
- 정책 방향, 제도 도입, 예산·사업 타당성, 대외 보고, 간부 의사결정처럼 **출처 있는 종합 판단**이 필요한 경우에는 `deep-research-pro` 방식을 우선한다.
- `deep-research-pro`의 핵심은 많은 자료가 아니라 **연구 질문 분해 → 다중 출처 확인 → 핵심 출처 본문 확인 → 인용 있는 종합**이다.
- 이 워크스페이스에서는 원문에 적힌 `/home/clawdbot/.../ddg`, `curl`, `~/clawd/research` 경로를 그대로 쓰지 않는다. 대신 OpenClaw의 `web_search`, `web_fetch`, `browser`, 필요 시 `korean-law` 도구를 사용하고, 저장이 필요하면 현재 workspace 아래 `outputs/reports/` 또는 사용자가 지정한 위치를 쓴다.

운영 원칙:

- 보고서 질문이 흐릿하면 별도 보조 스킬을 부르지 말고, 보고서셋 내부에서 목적·독자·결정사항·제약조건을 먼저 좁힌다.
- 자료 수집은 범용 자료수집 스킬을 부르지 말고, 공공기관 근거 우선순위에 따라 필요한 근거만 선별한다.
- 보조 조사 결과는 최종 문서에 그대로 붙이지 않고, `작성 방향`, `근거`, `쟁점`, `대안`, `보완 필요사항`에 녹인다.
- 시간이 촉박한 간부보고는 심층조사를 길게 돌리지 말고, 핵심 근거 3~5개와 쟁점 1~3개만 빠르게 정리한다.

## 1단계. 근거 확인

보고서 주제가 사실, 정책, 법령, 지침, 통계, 사례와 연결되면 먼저 근거를 확인한다.

확인할 근거:

- 관련 법령·지침·정부 발표
- 기관 내부 현황 또는 제공 자료
- 유사 기관 사례
- 통계·수치·예산·일정
- 반대 논리와 리스크
- 결정에 영향을 주는 제약 조건

원칙:

- 확인되지 않은 숫자, 일정, 법령, 지침은 단정하지 않는다.
- 근거가 부족한 내용은 `가정`, `추정`, `추가 확인 필요`로 표시한다.
- 단순 배경자료보다 의사결정에 필요한 근거를 우선한다.

---

## 2단계. 문서 유형 판별

요청 내용을 보고 문서 유형을 먼저 정한다.

| 유형 | 목적 | 기본 구조 |
|---|---|---|
| 검토보고 | 판단·승인 요청 | 배경 → 쟁점 → 대안 비교 → 검토의견 → 향후 조치 |
| 계획보고 | 추진계획 제시 | 추진배경 → 목표 → 추진내용 → 일정·역할 → 기대효과·리스크 |
| 결과보고 | 결과와 후속조치 보고 | 개요 → 추진결과 → 성과·한계 → 개선사항 → 향후계획 |
| 간부보고 | 빠른 판단 지원 | 결론 → 핵심근거 → 쟁점/대안 → 요청사항 |
| 회의결과 | 논의·결정·후속조치 정리 | 회의개요 → 주요논의 → 결정사항 → 후속조치 |
| 동향보고 | 외부 변화와 시사점 전달 | 핵심동향 → 영향 → 시사점 → 대응방향 |

---

## 3단계. 작성 기법 선택

문서 유형에 맞는 기법을 내부 사고 도구로 사용한다. 기법명은 최종 문서에 과하게 노출하지 않는다.

| 문서 유형 | 내부 적용 기법 |
|---|---|
| 검토보고 | MECE, 이슈트리, 대안평가, So What/Why So |
| 계획보고 | 5W3H, SMART, RACI, Risk Matrix |
| 간부보고 | BLUF, 피라미드 원칙, 1 Page Memo |
| 문제진단 | 로직트리, 5 Whys, Fishbone |
| 동향보고 | PEST, 3C, Signal/Noise |
| 회의결과 | Decision Log, 5W1H, RACI |

목차 밀도:

- 간부보고·1페이지 보고는 3~5개 큰 항목을 기본으로 한다.
- 검토보고·계획보고는 5~7개 큰 항목 이내를 권장한다.
- 세부 기법은 표, 문단, 점검 항목 안에 녹이고 제목으로 과하게 드러내지 않는다.

## 4단계. 공문서 보고서 초안 작성

초안은 아래 원칙을 따른다.

- 첫 문단 또는 첫 항목에서 결론·요청사항을 제시한다.
- 배경 설명보다 판단에 필요한 쟁점을 먼저 정리한다.
- 사실, 해석, 권고를 구분한다.
- 대안이 있으면 비교표를 사용한다.
- 추진계획에는 담당, 일정, 산출물, 점검 기준을 넣는다.
- 리스크는 나열하지 말고 대응책까지 붙인다.
- 소제목은 세세하게 쪼개지 말고 상위 묶음으로 정리한다.

문체:

- 기본 문체는 **개조식**으로 작성한다.
- 문장은 `~임`, `~하였음`, `~필요`, `~판단`, `~예정`, `~작성`, `~검토`처럼 공문서 보고서형 종결을 사용한다.
- 서술형 문장(`~합니다`, `~입니다`, `~것으로 보입니다`)은 보고서 본문에서 사용하지 않는다.
- 과장하지 않는다.
- 책임 없는 표현을 줄인다.
- `검토 필요`라고만 쓰지 말고 무엇을 결정해야 하는지 쓴다.
- `추진 예정`이라고만 쓰지 말고 누가 언제 무엇을 할지 쓴다.
- 공공기관 문체를 유지하되 문장을 지나치게 장황하게 만들지 않는다.

---

## 5단계. 논리·누락 검토

초안 작성 후 아래를 점검한다.

- 결론이 앞에 있는가?
- 의사결정자가 해야 할 판단이 보이는가?
- 근거 없는 숫자나 일정이 들어가 있지 않은가?
- 쟁점과 대안이 구분되어 있는가?
- 추천안의 이유가 분명한가?
- 실행 주체와 일정이 있는가?
- 리스크와 보완책이 함께 있는가?
- 목차와 소제목이 과도하게 세분화되어 있지 않은가?

---

## 6단계. 한글 문장 교정

마지막으로 한글 문장 품질을 정리한다.

점검 범위:

- 맞춤법과 띄어쓰기
- 조사와 어미의 자연스러움
- 중복 표현
- 장황한 문장
- 어색한 직역투
- 공공기관 보고서에 맞지 않는 과한 구어체

## 기본 출력 형식

사용자가 별도 양식을 주지 않으면 아래 순서로 답한다.

```markdown
## 작성 방향

- 문서 유형:
- 예상 독자:
- 핵심 목적:
- 먼저 확인한 근거:
- 내부 적용 기법:

## 초안

[공문서 보고서 형식의 초안]

## 보완 필요사항

- [추가 확인이 필요한 근거]
- [내부 결정이 필요한 사항]
```

최종 문서만 요청한 경우 `작성 방향`은 짧게 줄이고, 초안을 먼저 제시한다.
