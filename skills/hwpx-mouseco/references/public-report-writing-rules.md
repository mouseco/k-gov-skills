# 보고서 작성 규칙

## 전체 짜임새

- 보고서는 단편 문단 나열이 아니라 전체 골격이 먼저다.
- 문서 목적에 따라 `배경/현황 → 문제/필요성 → 기본방향 → 추진과제 → 관리방안/기대효과 → 향후 조치` 흐름을 선택한다.
- `도입 방안`, `추진 계획`, `개선 방안` 문서는 추진과제에서 끝내지 않는다. 기대효과, 관리지표, 향후 일정, 의사결정 요청 중 최소 하나로 닫는다.
- `1페이퍼`, `원페이퍼`, `1장 요약` 요청은 실제 페이지 분량이 최우선 제약이다. 분량이 부족하면 설명을 줄이고 결론부는 짧게 남긴다.

## 문단 위계

- 글머리 기호보다 문단 역할을 먼저 판정한다.
- 같은 논리 역할의 병렬 항목은 같은 글머리 위계로 배치한다.
- `첫째`, `둘째`, `셋째`는 같은 수준의 추진과제이므로 같은 글머리 기호를 사용한다.
- 하위 글머리는 상위 항목의 근거, 세부 실행, 보충 설명에만 사용한다.
- 병렬 항목을 `□`, `ㅇ`, `-`에 각각 나눠 넣으면 위계가 깨진 것으로 본다.
- `※`나 당구장표시는 주의, 참고, 예외, 관리 기준 등 note 성격에 우선 사용한다.

## 개조식 문체

- 보고서 본문은 원칙적으로 개조식 문체를 사용한다.
- 종결은 `~임`, `~함`, `~필요`, `~예정`, `~가능`, `~곤란`, `~우려`, `~했음`처럼 간결하게 쓴다.
- 개조식 종결 뒤에는 마침표를 찍지 않는다.
- `~합니다`, `~해야 합니다`, `~것입니다`를 반복하지 않는다.
- 제목, 요약 박스, 대외 공개용 문구처럼 자연문이 더 적절한 영역은 예외로 둘 수 있다.
- 한 문서 안에서는 종결 어미와 톤을 일관되게 유지한다.
- 각 문단은 독립적으로 읽혀도 의미가 통해야 한다.

## 작성자 메타

- 문서 상단의 날짜 옆 표기는 보통 `작성 부서 / 팀 / 작성자` 영역이다.
- 예: `< ’26. 1. 27.(화), 디지털혁신부 AI기획팀 >`에서 날짜 뒤 문자열은 문서 주제나 임의 태그가 아니라 작성 조직명이다.
- 이 영역에 `전략 검토 / sample organization 미래방향`처럼 임의의 문서 성격이나 주제를 넣지 않는다.
- 작성 부서, 팀, 작성자를 사용자가 주지 않으면 템플릿 기존 조직명을 보존하거나 확인한다.
- 공용 도구 JSON에는 가능하면 `authoring.date`, `authoring.department`, `authoring.team`, 선택 `authoring.name`으로 분리해 넣는다.

## 강조와 표현 형식

- 굵게 표시는 핵심어, 판단어, 정책 방향, 수치, 일정, 결론 중심으로 짧게 적용한다.
- 문장 전체를 굵게 하지 않는다.
- 한 문단 안의 굵게 표시는 보통 1~2개 구간으로 제한한다.
- 같은 위계의 병렬 항목은 강조 방식도 일관되게 맞춘다.
- 강조는 구조를 대신하지 않고, 이미 정리된 구조 안에서 시선을 돕는 보조 수단이다.
- 내용의 성격에 따라 표, 요약 박스, 비교형 정리, 단계형 정리, 주의/참고 박스 등을 검토한다.
- 템플릿의 기존 표현 수단이 있으면 우선 재사용한다.
- 장식성 표나 도식은 피하고 전달력을 우선한다.
